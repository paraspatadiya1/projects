Case study: Aura SIS

Purpose

A Student Information System with a REST API. It stores students and course programs, supports search and filtering, and exposes the same endpoints to browsers (as an HTML dashboard) and to API clients (as JSON). It's a personal portfolio project.

What it solves

Keeps student and course records in one structured database instead of loose files, and makes the data reachable from a browser UI or any HTTP client.

Backend architecture

Client→urls.py→views.py (@api_view)→serializer.py→models.py (ORM)→SQLite

A small helper inspects the Accept header (or ?format=json) and decides whether to return DRF JSON or render an HTML template, so one view serves both audiences.

API functionality

GET /getall/List students. Search by name, email, city or phone; filter with ?course=
GET /getid/<id>/One student
POST /addstudent/Create a student
PUT /updateid/<id>/Update a student
DELETE /deleteid/<id>/Delete a student
GET /getcourse/List courses with student counts
POST /addcourse/Create a course (also /getcourseid/, /updatecourse/, /deletecourse/)
GET /api/stats/Aggregated numbers for the dashboard charts

Authentication & authorization

Not implemented in this version: the endpoints are open. Adding authentication is the most obvious next step.

Database structure

  • Course: course_name, course_fees, course_duration
  • Studinfo: full_name, email (unique), phone, age, gender, city, address, and a foreign key to Course (students are reachable from a course via related_name="students")
  • SQLite in the repository configuration, with Django migrations

Engineering decisions

  • Serializer-level validation: negative course fees and ages outside 1–120 are rejected
  • Dashboard numbers (totals, average age, enrollment per course, gender split) are calculated in Django and passed to Chart.js
  • Routes are registered with and without a trailing slash so API clients work either way
  • A seed_data management command loads sample records
  • 11 test cases cover CRUD, search, course filtering, validation and the stats endpoint

Deployment

Runs on Render with Gunicorn and WhiteNoise for static files. The repository includes a build script (install, collectstatic, migrate) and a PythonAnywhere deployment guide.

Case study: paras.dev Portfolio

Purpose

A Django-served portfolio with a real backend behind the contact form, rather than a static page.

How the contact form works

Form (fetch + CSRF token)→POST /contact/→validate→save ContactMessage→send emails
  • The view accepts a JSON body, checks that all fields are present and the email is valid, and returns clear JSON errors
  • Each message is stored in the database before any email is sent, so nothing is lost if email delivery fails
  • One email notifies me (with a reply-to of the sender); a second is a confirmation to the visitor
  • Messages can be browsed and searched in Django admin

Front end

Plain HTML, CSS and JavaScript. A Three.js hero scene and GSAP scroll motion are layered on top, and both have static fallbacks. Five themes persist across visits, the interface is keyboard-accessible, and it respects reduced-motion settings.
